# Initiative Generation & Deterministic Initiative Ordering

## Overview

Initiative in GameMasterX is **generated by backend rules** through the shared
dice subsystem, and the resulting **initiative order is deterministic and stable
for ties**. Round and turn tracking are established from that order, and every
initiative roll is **auditable** with the encounter revision before and after the
recorded.

Initiative is never trusted from the wire. Instead it is resolved server-side by
rolling a `1d20` for each participant through the same `DiceRoller` that backs
the `/api/dice` endpoints, and the combat order is derived from the resolved
scores.

## Package layout

| Type | Responsibility |
| ---- | -------------- |
| `encounter/service/InitiativeService` | Single authority that rolls initiative for each participant through the dice subsystem and assigns the scores. |
| `encounter/service/InitiativeService.InitiativeResult` | Auditable per-participant initiative roll (die value, initiative score, die result, mode/seed). |
| `encounter/service/InitiativeService.Rollout` | The audit trail of a generation: the initiative order, results and revision before/after. |
| `encounter/controller/InitiativeResponse` | API response: the established initiative order plus one auditable result per participant. |
| `encounter/service/EncounterService` | Wires initiative generation into the encounter lifecycle (`startEncounter`, `generateInitiative`). |
| `encounter/controller/EncounterController` | REST surface on the backend API port (5172). |
| `gameplay/model/ActionType#INITIATIVE` | Typed category for an initiative action in the immutable audit log. |

## Initiative is generated from the dice subsystem

`InitiativeService.generate` rolls a `1d20` for every participant using a single
shared `DiceRoller`. One roller drives every participant so that each participant
draws a **distinct** die value from one generator state. In `SEEDED` mode the
roller is seeded from a stable FNV-1a hash of the seed (the same mechanism used
by the dice API), so rolling the same participants with the same seed always
produces the same initiative scores and therefore the same combat order. In
`RANDOM` mode the values are drawn from a cryptographically strong generator and
the individual die value is recorded on each `DiceResult` for later verification.

Each participant's initiative score is the resolved `1d20` value, written back
onto the `Participant`. The `InitiativeResult` for each participant records the
`roll`, the `initiative` score, the full `dieResult`, the applied `rollMode` and
the `seed` (when seeded).

## Deterministic and stable ordering

The initiative order is computed by `Encounter.recomputeInitiativeOrder`, a
stable descending sort by initiative score. Ties are broken by the participant's
original insertion order, so the order is **deterministic and reproducible** for
a given set of scores. Because the scores themselves are deterministic under a
seed, the initiative order is deterministic and stable for ties.

## Round and turn tracking established from the order

The round/turn tracking is established from the initiative order:

- `round` starts at `1`.
- Starting (or resuming) the encounter sets the acting turn index `turn` to `0`
  into the freshly computed `initiativeOrder`.
- `advanceTurn` walks the `initiativeOrder`, wrapping to the next round when the
  list is exhausted.

`startEncounter` therefore always establishes the combat order from the dice
subsystem before positioning the encounter at turn `0` of round `1`. If a
participant already carries a pre-set initiative score it is respected; any
participant without a score is rolled so that the combat order is ultimately
owned by backend rules. A dedicated `generateInitiative` step lets the game
master re-roll initiative while the encounter is still in the `DRAFT` state.

## Auditable with revision before and after

Each initiative generation is appended to the immutable turn and audit history:

- A single `Turn` document embeds one `Action` of type `INITIATIVE` carrying
  every participant's `DiceResult`, together with the encounter revision before
  and after.
- One accepted `Mutation` per participant records the initiative score's
  `before` (`null`) and `after` state.
- Each `Audit` entry records the `ACCEPTED` decision with the `revisionBefore`
  and `revisionAfter`, so the initiative results are auditable and prior turns
  are never updated.

The turn and audit history is surfaced on the backend API port (5172) through
`GET /api/encounters/{id}/turns` and `GET /api/encounters/{id}/audit`.

## API contract

| Method & path | Action |
| ------------- | ------ |
| `POST /api/encounters/{id}/start` | Start the encounter, rolling initiative for any participant without a pre-set score. |
| `POST /api/encounters/{id}/initiative` | Re-roll initiative for every participant in a DRAFT encounter. |
| `GET /api/encounters/{id}/turns` | Return the immutable turn history (includes initiative-generation turns). |
| `GET /api/encounters/{id}/audit` | Return the immutable audit log (includes initiative decisions with revision before/after). |

### `POST /api/encounters/{id}/initiative`

Query parameters:

| Field | Type | Notes |
| ----- | ---- | ----- |
| `rollMode` | string | `"random"` (default) or `"seeded"`. Case-insensitive. |
| `seed` | string | Required when `rollMode` is `"seeded"`; ignored otherwise. |

Returns the updated `EncounterDto` and an `InitiativeResponse`:

| Field | Type | Notes |
| ----- | ---- | ----- |
| `initiativeOrder` | `string[]` | Participant ids in descending initiative order. |
| `results` | `InitiativeResult[]` | One auditable result per participant, in participant order. |

Each `InitiativeResult`:

| Field | Type | Notes |
| ----- | ---- | ----- |
| `participantId` | string | The participant the roll was made for. |
| `participantName` | string \| null | The participant's name. |
| `initiative` | number | The initiative score assigned (the `1d20` total). |
| `roll` | number | The raw `1d20` value that was rolled. |
| `dieResult` | `DiceResult` | The auditable die record resolved through the dice subsystem. |
| `rollMode` | string | `"random"` / `"seeded"`. |
| `seed` | string \| null | The seed that produced the roll, or null for random mode. |
| `rolledAt` | string | Timestamp the roll was resolved. |

### Error handling

- A `seeded` roll (start or generate) with a missing or blank seed is rejected
  with a `400 BAD_REQUEST`.
- An unrecognized `rollMode` is rejected by the dice subsystem's `RollMode`
  parsing with a `400 VALIDATION_ERROR`.
- Generating initiative requires the DRAFT state and at least one participant;
  other states yield a `400 BAD_REQUEST` and an empty encounter yields a
  `404`/`400` as appropriate.
- All endpoints require an authenticated actor; unauthenticated callers receive
  `403 FORBIDDEN`.

## Reproducing a seeded initiative order

Because seeded initiative rolls are deterministic, the same combat order can be
replayed by re-running the generation with the same `rollMode` and `seed`; each
`InitiativeResult.dieResult()` records the exact die values that were drawn.
